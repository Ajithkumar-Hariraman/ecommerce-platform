# AWS interview guide

Deployment is still in progress. Explain implemented mechanisms separately from
live verification: see aws-deployment.md and current-state.md. A design diagram
or successful Terraform apply does not prove customer checkout.

| Concept | WHAT | WHY | WHERE USED | HOW IT WORKS | FAILURE SCENARIO | 30-SECOND INTERVIEW ANSWER |
|---|---|---|---|---|---|---|
| ECS | Container scheduler | Manage desired workloads | Five planned services and explicit migration tasks | Places task definitions and replaces failed service tasks | Bad image or failed health check causes deployment failure | ECS manages our services and their desired task counts. The API, web, identity server and two workers have separate definitions and roles. We wait for stability after deployment; a running task alone does not establish application readiness. |
| Fargate | Managed container compute | Avoid managing EC2 hosts | All application tasks | Allocates requested CPU/memory and ENI | Account vCPU quota or image-pull failure prevents placement | Fargate provides compute while ECS schedules it. We request 2.25 vCPU at steady state and budget rolling overlap below eight vCPU. Tasks get public IPs for egress, with security groups preventing direct inbound access. |
| Task definition | Versioned launch specification | Reproducible releases | Per-workload families | Declares image, command, limits, role, secrets and logs | Wrong command or secret reference prevents startup | A task definition is the release recipe. It contains an immutable image identifier and configuration references. Registering it does not deploy it; a service update or RunTask selects a revision. |
| Service | Long-lived desired-state controller | Replace failures and roll releases | Web/API/Keycloak/relay/worker | Maintains desired count and optional target registration | Process crash causes replacement; repeated crashes need investigation | Services keep long-running tasks available and control deployment overlap. We use circuit breakers and health checks. The migration is excluded because it must finish once and gate the release rather than restart indefinitely. |
| Task | One launched workload instance | Isolated runtime execution | Fargate containers and migration RunTask | Starts containers from one definition with an ENI | Essential container exits | A task is an actual execution of a task definition. We inspect exit codes for migrations and service health for long-running tasks. The definition may be valid while a task fails because of IAM, networking or database readiness. |
| ALB | Layer-seven load balancer | Share ingress and route paths | Dedicated ecommerce ALB | Listener rules forward to IP target groups | Wrong route or unhealthy target returns errors | One ALB routes the storefront, API and identity paths to separate target groups. Security groups allow only ALB-to-task traffic. Health checks establish target readiness, while public HTTPS awaits a user-owned domain and regional ACM validation. CloudFront is optional and does not block ECS. |
| Target group | Backend registration and health policy | Separate routing from tasks | Web/API/Keycloak groups | ECS registers task IPs, ALB probes paths | Wrong port or health path drains all targets | A target group collects routable task endpoints. Our API target uses port 3000 and readiness checks; web and Keycloak use 8080. Port agreement among container, task and target group is essential. |
| ECR | Private image registry | Store release artifacts | Three dedicated ecommerce repositories | Docker pushes layers/manifests; execution role pulls | Missing image or expired release tag breaks launch | ECR stores the AMD64 images that ECS pulls. We use immutable Git/source identifiers and lifecycle cleanup, not latest. The account's unrelated repository is untouched, and old deployed releases must remain available for recovery. |
| RDS | Managed relational database | Preserve ACID business state | Private PostgreSQL 16 | AWS manages instance/backups; app uses verified TLS SQL | Connection exhaustion or unavailable instance affects readiness | RDS stores orders, payments, outbox and notifications with SQL transactions. We chose a small Single-AZ development instance, encrypted storage and backups. TLS verifies the RDS hostname and CA; runtime, migration and identity credentials are separate. |
| ElastiCache | Managed in-memory cache | Cache reads and coordinate limits | Private Valkey node | TLS/authenticated Redis protocol commands | Cache outage removes acceleration/limiting | Valkey supports cache-aside products and atomic rate-limit counters. The database remains authoritative. Existing deliberate fail-open behavior preserves application availability during cache failure, but also means rate limiting is not enforced while the cache is unavailable. |
| S3 | Durable object storage | Private images and PDFs | Separate versioned product/document buckets | Conditional writes and immutable versions | Replay upload or invalid content must be rejected | S3 stores objects outside the SQL database. We block public access, encrypt and version objects, and require create-only writes. Product references persist VersionId so a later read targets exactly the validated content rather than a mutable key. |
| Presigned URL | Time-limited delegated request | Browser transfer without AWS credentials | Product upload/download | SigV4 signs operation, key, headers and expiry | Leaked URL works until expiry; changed headers invalidate it | A presigned URL grants a narrow temporary S3 operation. Uploads bind type, length and If-None-Match, and downloads bind VersionId. It is a bearer capability, so we keep expiration short and do not log it. |
| SNS | Push fan-out topic | Decouple outbox from consumers | OrderPaid topic | Publishes JSON and attributes to subscribed SQS | Publish fails; outbox lease/backoff retains intent | The relay publishes committed outbox events to SNS. Publishing is separate from the payment transaction, so failures retry without losing durable intent. Sending before recording success can duplicate delivery; downstream event-ID deduplication is therefore required. |
| SQS | Durable message queue | Buffer work and absorb outages | Notification queue | Long polling returns messages with receipt handles | Worker crashes before deletion, causing redelivery | SQS buffers notifications between SNS and the worker. Delivery is at-least-once. We delete after durable processing, use long polling and bounded retries, and accept safe duplicates rather than claiming exactly-once transport. |
| DLQ | Queue for exhausted messages | Isolate poison work | Notification dead-letter queue | Source redrive policy moves messages after five receives | Unmonitored DLQ hides failed notifications | Our DLQ retains failed messages for 14 days and has a visible-message alarm. Operators inspect sanitized event context, fix the underlying issue and replay deliberately. Moving a poison message back without repair only repeats the failure. |
| Visibility timeout | Temporary delivery lease | Give a worker time to finish | Source queue, initially 60 seconds | Received message becomes temporarily invisible | Too short creates concurrent duplicate processing | Visibility timeout does not acknowledge a message. If a worker crashes, its message becomes available again. We start at 60 seconds, measure handling time and retain durable idempotency; longer work may need visibility extensions. |
| Execution role | ECS agent permissions | Pull images and resolve startup secrets | Dedicated role per workload | ECS uses it before/container startup and logging | Missing GetSecretValue blocks initialization | The execution role belongs to the ECS launch process. It pulls ECR images, resolves only required secret ARNs and writes the workload's logs. Application business code uses a different role with its own restricted permissions. |
| Task role | Container AWS identity | Enforce application least privilege | API/relay/worker identities | AWS SDK obtains rotating task credentials | Overbroad policy increases blast radius | The task role defines what application code can call. API accesses scoped S3 keys, relay publishes to one topic, and worker consumes one queue plus documents. Web and Keycloak need no general AWS API access. |
| Secrets Manager | Managed secret store | Keep credentials out of Git/images | DB/cache/Keycloak/Razorpay | ECS resolves specific secret versions on launch | Rotation without task replacement leaves stale credentials | Secrets Manager holds private runtime values. Task definitions reference names or ARNs, never plaintext passwords. Updating a secret does not automatically replace every running process, so rotation needs coordinated credential and task lifecycle management. |
| CloudWatch | Logs, metrics, dashboards, alarms | Diagnose and detect failures | Per-task logs, dashboard, nine alarms | Services emit metrics; alarm rules evaluate windows | Missing data can hide a service that never started | CloudWatch combines structured task logs with service and data metrics. We use bounded log retention and conservative thresholds. Console alarms currently have no external recipient, and missing metrics are not evidence that the system is healthy. |
| GitHub OIDC | Federated short-lived CI identity | Avoid stored AWS keys | Exact repo and deployment branch trust | GitHub token is exchanged by AWS STS | Wrong subject/audience cannot assume role | OIDC gives the deployment job temporary AWS credentials. Trust matches this repository, exact deployment branch and STS audience. Permissions allow ECR/ECS deployment and restricted PassRole, while Terraform administration and database passwords remain separate. |
| Terraform | Declarative infrastructure/state engine | Review and reproduce infrastructure | Separate AWS bootstrap/dev trees | Plans compare configuration, state and provider observations | Partial apply requires refresh and repair | Terraform provisions dedicated resources using reviewed plans. State is versioned and encrypted in S3 with native lockfiles. A partial apply is reported honestly and repaired; it is not a reason to reset databases or destroy unrelated resources. |
| VPC | Isolated regional network | Control routing/security boundaries | Dedicated ecommerce-dev network | Subnets, route tables and security groups define reachability | Accidental route or ingress exposes a dependency | The VPC separates public ingress/egress from private data services. It spans two AZs. RDS and Valkey never receive public addresses, while application task security groups enforce who may connect even when tasks have public egress IPs. |
| Subnets | AZ-specific address ranges | Separate placement and routes | Two public and two private data subnets | Public routes reach IGW; data routes stay local | Wrong subnet/route prevents image pulls or exposes services | A subnet's route table determines internet reachability. We use public task subnets to avoid NAT cost and private subnets for data. Two subnet AZs provide placement options, although a Single-AZ database remains a deliberate availability limitation. |
| Security groups | Stateful network allow rules | Restrict workload reachability | Separate ALB/task/database/cache groups | Source-group rules authorize exact ports | Broad CIDR ingress defeats isolation | Security groups implement least network access. Only ALB may enter frontend/API/identity task ports. Workers have no ingress, RDS accepts specific task groups on 5432, and Valkey accepts the API group on 6379. Public IP does not imply permitted inbound traffic. |

## Current HTTPS decision

ALB + regional ACM is the intended current HTTPS path. CloudFront is optional
future infrastructure. No usable owned domain was found, so neither a fabricated
hostname nor insecure HTTP is presented as completion. Stable private workloads
and gated API checks demonstrate deployment progress, not browser/payment E2E.
See aws-status.md for observed results and the completion matrix.
