# Product image assets

Cloud Storage holds private image bytes; the selected business repository holds only the validated bucket, object name, immutable generation, MIME type and byte count. No signed URL is persisted in Product or Redis.

Catalog managers/admins request POST /api/v1/products/:id/image-upload with contentType and size, upload the File directly to the returned signed PUT URL, then PUT /api/v1/products/:id/image with objectName. Readers request GET /api/v1/products/:id/image-url for a short-lived signed GET. Existing authentication, RBAC and rate limiting apply; no API Bearer token is sent to Cloud Storage.

JPEG, PNG and WebP are limited to 5 MiB. Signed V4 requests bind Content-Type and exact Content-Length and require x-goog-if-generation-match: 0. The browser supplies Content-Length automatically from the File. Keys are generated by the server under the Product UUID, so clients cannot select arbitrary destinations or overwrite existing objects. Signed uploads expire after 300 seconds by default (validated range 60–900).

Before attachment the backend checks namespace, object metadata/size and the first 32 bytes against format signatures. The resulting generation is pinned for subsequent reads. This is bounded type/header validation, not a full image decoder or malware scan. SVG and executable formats are rejected. Invalid/unattached uploads remain private; stale-object lifecycle/retention is a separate operational policy. Product deletion does not synchronously delete an object or create a database/storage transaction illusion.

PostgreSQL migration 010 adds nullable image_asset; historical Products remain unchanged. Mongo stores the same optional image object without a schema reset. Product updates retain it; attachment invalidates the Product cache only after database success. The UI retains a newly created Product ID after upload failure so retry does not create another Product.

Configuration: PRODUCT_ASSET_BUCKET, GOOGLE_CLOUD_PROJECT, PRODUCT_ASSET_SIGNER_SERVICE_ACCOUNT and PRODUCT_ASSET_URL_TTL_SECONDS. An empty bucket disables image endpoints with safe 503 without affecting ordinary CRUD. Errors never return provider details or signing credentials.

Signing uses Google SDK ADC plus keyless service-account impersonation/signBlob. The runtime identity needs bucket-scoped object permissions and signing permission on itself. A local operator additionally needs explicit Token Creator permission on the target service account; that enables impersonation of its runtime privileges and must be approved separately. Verification used an explicitly approved temporary binding, removed immediately afterward and verified absent. No JSON private key is required.

Bucket CORS must allow the exact frontend origins and PUT/GET/HEAD headers. infra/gcp/product-assets-cors.json contains only the local 127.0.0.1 origin; append the deployed Web HTTPS origin before cloud browser use. CORS does not replace authorization or make the bucket public.

Automated verification: focused validation, signed-header, generation, safe-failure, RBAC, cache and Product regressions passed; real Postgres/Mongo ecommerce_test persistence passed with own-record cleanup. Real signed GCS upload/download, generation pinning and overwrite rejection passed. The opt-in test created/removed only one unique test-owned object. Production deployment and browser CORS behaviour remain unverified.

Reference: [Google V4 signing](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers) and [PUT Object preconditions](https://docs.cloud.google.com/storage/docs/xml-api/put-object).
